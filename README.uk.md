# security-watch

![security-watch: журнали, порти, процеси та база даних ліворуч; один виконуваний файл на Go у центрі; Телеграм, пошта, HTTP API та файлові звіти праворуч](assets/banner.png)

Служба спостереження за сервером для Linux. Читає журнали, стежить за файлами,
портами, процесами та базою даних і повідомляє про помічене у файл, у Телеграм,
на HTTP-приймач або листом. Нічого в системі не змінює, доки її про це не
попросять.

Один виконуваний файл на Go без зовнішніх залежностей, окрім драйверів СУБД.
Налаштовується одним файлом JSON. Встановлюється як служба systemd. Привʼязки до
певного застосунку немає: усе, що залежить від сервера, задається
налаштуваннями.

## Що робить

| Джерело | Що помічає |
|---|---|
| Журнал веб-сервера | перебір шляхів, підбір доступу, навала запитів, звернення до пасткових шляхів, ознаки впровадження в рядку запиту |
| Журнал входів | підбір пароля через SSH, успішний вхід (окремо - з незнайомої адреси), запуск через sudo |
| Журнал застосунку | повідомлення СУБД про зіпсований запит, власні ознаки, ознаки впровадження в тілі запиту |
| Файли | підміна, додавання, вилучення, зміна прав; обходом за розкладом і тієї ж миті через inotify |
| Порти, що слухають | поява порту, якого немає в заявленому списку; зникнення заявленого |
| Процеси | запуск із тимчасового каталогу, робочий процес із вилученим файлом, вихідне зʼєднання на незаявлений порт |
| База даних | перевищення порогу власним запитом, зміна полів, які застосунок змінювати не повинен |
| auditd | запуск програм із повним командним рядком, читання файлу-принади |
| Дзеркало запитів nginx | впровадження та підстановка привілейованих полів у тілі POST і в заголовках |
| Пастка | звернення до адреси, на яку немає жодного посилання |
| Принади | поява підробленого ключа в будь-якому спостережуваному журналі |
| Сама служба | зупинка, підміна власних файлів, ознака життя, власні лічильники |

Понад спостереження служба вміє склеювати повтори, здобувати відомості про
адресу (зворотне імʼя, власник мережі за RDAP, належність до мережі Tor), вести
рахунок за кожною адресою, вчити звичайну поведінку сервера й повідомляти про
відхилення, нумерувати події ланцюгом відбитків, збирати пропозиції щодо
блокування з доказами, видавати нападникові підроблений ключ і пов'язувати його
з наступною спробою входу.

## Чого не робить

- Не блокує й не змінює систему за власним рішенням. Блокування - окрема
  команда; самостійне блокування вимкнене за замовчуванням і включається з
  умовами.
- Не розбирає мережеві пакети й не вбудовується в ядро. Відомості рівня ядра
  беруться готовими з журналу auditd.
- Не надсилає вміст спостережуваних файлів нікуди - рахує лише відбитки SHA-256.
- Не лізе на машину нападника. Збирається тільки те, що він надіслав сам, плюс
  відкриті дані реєстрів (RDAP, зворотний DNS).
- Не заміна WAF і антивірусу. Це спостерігач, а не захист периметра.

## Вимоги

- Linux. Розбір `/proc/net/tcp`, `/proc` та inotify - лінуксові; на інших
  системах стеження в реальному часі вимикається, решта працює.
- Go 1.25 або новіший для збірки. На сервері Go не потрібен.
- Права root: для читання `/var/log/auth.log`, каталогів інших користувачів і
  `/proc`.
- Необовʼязково: `auditd` (відомості рівня ядра), nginx з директивою `mirror`
  (розбір тіла запиту), MySQL/MariaDB або PostgreSQL (перевірки в базі).

## Встановлення

Збірка та встановлення на тому самому сервері:

```bash
git clone https://github.com/Insider515/security-watch-daemon.git
cd security-watch-daemon
sudo ./install.sh
```

`install.sh` збирає виконуваний файл, розкладає його по каталогах, ставить
службу systemd, правило logrotate і, якщо файлу налаштувань ще немає, кладе
приклад. Повторний запуск оновлює лише виконуваний файл і перезапускає службу,
налаштувань не торкається.

Якщо на сервері немає Go, зберіть у себе й скопіюйте один файл:

```bash
GOOS=linux GOARCH=amd64 go build -ldflags='-s -w' -o security-watch ./cmd/security-watch
scp security-watch root@сервер:/tmp/
scp systemd/security-watch.service root@сервер:/etc/systemd/system/
scp config.example.json root@сервер:/tmp/
ssh root@сервер '
  mkdir -p /opt/security-watch /etc/security-watch /var/lib/security-watch /var/log/security-watch
  chmod 750 /var/lib/security-watch /var/log/security-watch
  install -m 0755 /tmp/security-watch /opt/security-watch/security-watch
  install -m 0640 /tmp/config.example.json /etc/security-watch/config.json
  systemctl daemon-reload && systemctl enable --now security-watch
'
```

Unit systemd постачається з обмеженнями: `NoNewPrivileges`,
`ProtectSystem=strict`, `ProtectHome=read-only`, `ProtectKernelTunables`,
`ProtectKernelModules`, `MemoryDenyWriteExecute`; запис дозволено лише до
каталогу стану та каталогу журналу подій.

## Швидкий старт

Найкоротший робочий файл налаштувань - журнал веб-сервера та файл подій:

```json
{
  "host": "my-server",
  "sinks": { "file": "/var/log/security-watch/events.jsonl" },
  "access_log": {
    "enabled": true,
    "path": "/var/log/nginx/access.log",
    "not_found_per_minute": 60,
    "requests_per_minute": 600,
    "detect_injection": true,
    "suspicious_paths": ["/.env", "/.git", "/wp-login.php", "/phpmyadmin"]
  }
}
```

Усе, що не задано, береться за замовчуванням. Перевірка налаштувань до запуску:

```bash
security-watch -config /etc/security-watch/config.json -check
```

Команда каже, яких із названих файлів і каталогів немає та чого бракує
увімкненим розділам. Те, що не перешкоджає роботі, виводиться заувагою, а не
помилкою.

Один прохід файлами, портами, процесами та базою без постійного спостереження:

```bash
security-watch -config /etc/security-watch/config.json -once
```

Перший прохід лише запамʼятовує поточний стан: порівнювати ще ні з чим, тому
подій він не дає.

## Як це працює

Кожна подія проходить один шлях:

```
джерело спостереження
  -> приглушення правилами ignore, поправка важливості severity_overrides
  -> склеювання повторів у вікні dedup_window
  -> відомості про адресу (зворотний DNS, RDAP, Tor)
  -> номер і відбиток попередньої події (ланцюг)
  -> пропозиція щодо блокування, якщо вид події є в propose_on
  -> рахунок дійової особи, навчання
  -> журнал служби
  -> приймачі: файл, Телеграм, HTTP, пошта
```

Порядок обрано за вартістю: зайве відкидається до того, як на подію витратяться
запити назовні та запис у ланцюг.

Кожен спостерігач працює власною горутиною: читання журналів іде безперервно,
обходи - за розкладом із налаштувань. Позначки прочитаного зберігаються на
диску, тому перезапуск не губить рядки й не перечитує старе.

## Джерела спостереження

### Журнал веб-сервера

Розділ `access_log`. Читає журнал рядок за рядком і розуміє стандартний формат
combined:

```
1.2.3.4 - - [30/Oct/2026:22:13:00 +0100] "POST /api/pay HTTP/2.0" 404 153 "-" "UA"
```

Порогові події рахуються за кожною адресою у вікнах по хвилині; на новій хвилині
рахунок починається заново, тому пороги ловлять спалахи, а не добові суми.

| Налаштування | За замовчуванням | Подія в разі перевищення |
|---|---|---|
| `not_found_per_minute` | 60 | `path_scan` - перебір шляхів |
| `denied_per_minute` | 30 | `access_denied_burst` - підбір доступу (401, 403) |
| `errors_per_minute` | 10 | `server_error_burst` - потік відповідей 5xx |
| `requests_per_minute` | 600 | `request_flood` - навала запитів |

Крім порогів, кожен рядок перевіряється на:

- `suspicious_paths` - шляхи, звернення до яких підозріле саме собою (`/.env`,
  `/.git`, `/wp-login.php`), подія `suspicious_path`;
- `honeypot_paths` - шляхи, яких на цьому сервері немає й бути не повинно, подія
  `honeypot_hit` з найвищою важливістю;
- `detect_injection` - ознаки впровадження в рядку запиту, див. [Ознаки
  впровадження](#ознаки-впровадження);
- принади з розділу `canary`, подія `canary_used`.

Нестандартний формат журналу задається власним виразом:

```json
"access_log": {
  "regexp": "^(?P<ip>\\S+) \\S+ \\[(?P<time>[^\\]]+)\\] \"(?P<method>\\S+) (?P<path>\\S+)[^\"]*\" (?P<status>\\d{3})",
  "extra_fields": ["ja3", "cf_ip"]
}
```

Розуміються імена дужок `ip`, `time`, `method`, `path`, `status`, `agent`;
решта потрапляє до подробиць події. `extra_fields` - імена доданих до
`log_format` полів у хвості рядка, за порядком: так до події потрапляє,
наприклад, відбиток TLS.

Якщо сайт працює за Cloudflare або іншим зворотним проксі, у журналі будуть
адреси проксі, а не клієнтів. Справжню адресу додають до `log_format`:

```nginx
log_format combined_real '$http_cf_connecting_ip - $remote_user [$time_local] '
                         '"$request" $status $body_bytes_sent '
                         '"$http_referer" "$http_user_agent"';
access_log /var/log/nginx/access.log combined_real;
```

Далі назвіть це поле в `extra_fields` і вкажіть його в `real_ip_field` - тоді
події несуть адресу клієнта, а не проксі:

```json
"access_log": { "extra_fields": ["ja3", "cf_ip"], "real_ip_field": "cf_ip" }
```

Порожнє або нерозбірливе значення поля пропускається, і береться адреса з
першого поля рядка. Якщо проксі пише список, береться перша адреса списку.

Шлях може бути зразком: `"/var/log/nginx/access-*.log"`. Читач бере найсвіжіший
відповідний файл - так влаштовані журнали, які щодня заводять новий файл із
датою в імені.

### Журнал входів

Розділ `auth_log`, за замовчуванням `/var/log/auth.log` (у RHEL і похідних -
`/var/log/secure`).

- Невдалі спроби накопичуються й дають `ssh_bruteforce` у разі перевищення
  `failures_per_minute` (за замовчуванням 5) за хвилину з однієї адреси.
- Успішний вхід дає `ssh_login`. Якщо адреса є в `known_ips` - важливість
  відомча, якщо немає - тривога. Це відрізняє "ломляться" від "уже ввійшли".
- Запуск через sudo дає `sudo` з користувачем і командою.

`known_ips` містить як точні адреси, так і мережі у вигляді CIDR:
`203.0.113.9`, `188.129.64.0/18`, `2001:db8::/32`. Якщо адреса провайдера
змінюється в межах однієї мережі, запис цієї мережі звільняє від тривоги на
кожен власний вхід.

Власні вирази для інших способів входу (панель, VPN, пошта):

```json
"auth_log": { "extra_failure_patterns": ["authentication failure for (\\S+) from (\\S+)"] }
```

Перша дужка - імʼя користувача, друга - адреса.

### Журнал застосунку

Розділ `app_log`. Впровадження частіше приходить тілом POST, якого в журналі
веб-сервера немає взагалі. Натомість СУБД, отримавши зіпсований запит, пише до
журналу застосунку впізнаване повідомлення про помилку розбору - ознака того,
що підставлене значення дійшло до бази. Подія `db_error` з найвищою важливістю.

Повідомлення MySQL/MariaDB та PostgreSQL вбудовані; окремо шукається ознака
того, що запит таки виконався й повернув службові таблиці. Вбудований набір
вимикається (`disable_builtin_patterns`), власні рядки додаються:

```json
"app_log": {
  "enabled": true,
  "path": "/var/log/myapp/app.log",
  "extra_patterns": ["mass_assignment", "guard_field"],
  "detect_injection": true
}
```

Пошук ознак впровадження в журналі застосунку включається окремо: у деяких
журналах такі рядки трапляються штатно.

### Файли

Розділ `files`. Порівнює поточний стан шляхів із попереднім зліпком: вміст за
SHA-256, права, час зміни. Зліпок лежить на диску, тому помічається й підміна,
що сталася під час простою служби.

```json
"files": {
  "enabled": true,
  "paths": ["/etc/nginx", "/etc/systemd/system", "/root/.ssh", "/etc/cron.d", "/opt/myapp/.env"],
  "interval": "5m",
  "max_depth": 6,
  "skip": ["node_modules", "/tmp/", ".git/"]
},
"files_realtime": true
```

`files_realtime` додає стеження через inotify: подія надходить у межах 0,3
секунди, а не на наступному обході (дескриптор опитується з таким терміном, щоб
служба зупинялася за сигналом протягом секунди). Обхід за розкладом залишається - він переживає перезапуск
служби й бачить те, що сталося під час її простою. Події реального часу мають
окремі види із суфіксом `_realtime`.

### Порти, що слухають

Розділ `ports`. Читає `/proc/net/tcp` і `/proc/net/tcp6` напряму, без `ss` і
`netstat`. Порт, якого немає в `expected`, дає `listening_port`; зникнення
заявленого порту - `port_gone`.

```json
"ports": { "enabled": true, "interval": "1m", "expected": [22, 80, 443, 3306] }
```

На першому проході незаявлені порти повідомляються попередженням (це опис
наявного), далі - тривогою.

### Процеси та вихідні зʼєднання

Розділ `processes`. Обходить `/proc` і шукає:

- `process_from_temp` - програму, запущену з `/tmp`, `/dev/shm`, `/var/tmp`,
  `/run/user` (список у `suspicious_dirs`);
- `deleted_binary` - процес працює, а його файл вилучено з диска;
- `outbound_connection` - вихідне зʼєднання на порт, якого немає в
  `allowed_outbound_ports`; зʼєднання до приватних адрес пропускаються.

```json
"processes": {
  "enabled": true,
  "interval": "1m",
  "suspicious_dirs": ["/tmp", "/dev/shm", "/var/tmp", "/run/user"],
  "allowed_outbound_ports": [25, 53, 80, 443, 587, 3306]
}
```

Якщо сервер у справах ходить на довільні порти (перевірка проксі, опитування
чужих API), перевірку вихідних краще приглушити правилом, залишивши два інші
види:

```json
"ignore": [{ "source": "process", "kind": "outbound_connection" }]
```

### База даних

Розділ `db`. Два різні види перевірок, обидва описуються налаштуваннями - у коді
запитів немає.

**Перевірки запитом** (`checks`). Запит мусить повертати один рядок з одним
числом; якщо число більше за `threshold`, видається `threshold_exceeded`. Запит
перевіряється на "тільки читання": дозволено починати із `SELECT` або `WITH`,
слова, що змінюють дані, заборонені; відкинутий запит дає `check_rejected`.

```json
"db": {
  "enabled": true,
  "driver": "mysql",
  "dsn": "watch:password@tcp(127.0.0.1:3306)/mydb?parseTime=true",
  "interval": "5m",
  "checks": [
    {
      "name": "registrations per hour",
      "query": "SELECT COUNT(*) FROM users WHERE created_at >= NOW() - INTERVAL 1 HOUR",
      "threshold": 10,
      "severity": "warn",
      "description": "A spike in registrations is a sign of a bot flood"
    }
  ]
}
```

**Спостереження за полями** (`column_watches`). Служба тримає зліпок вибраних
полів і повідомляє про доданий рядок (`row_added`), зниклий (`row_removed`) і
про зміну значення (`column_changed`) - із колишнім і новим значенням.

```json
"column_watches": [
  {
    "name": "user roles",
    "table": "users",
    "key": "id",
    "columns": ["role_id", "is_admin"],
    "where": "role_id IN (1,3,4)",
    "severity": "alert",
    "max_rows": 5000
  }
]
```

Це той випадок, який не видно ні в журналі веб-сервера, ні в журналі застосунку:
значення, записане до бази в обхід форми - підстановка привілейованого поля,
зміна через чужий доступ, зміна прямо в консолі СУБД. Обирайте поля, що
змінюються рідко: роль, ознака адміністратора, ключ API, налаштування. Поле, яке
змінюють часто, дасть тривогу на кожну зміну.

`where` звужує спостереження. Умова на кшталт `role_id <= 2` на сервері, де роль
звичайного користувача дорівнює 2, дасть тривогу на кожну реєстрацію.

Службі достатньо доступу лише на читання. Окремий користувач для MySQL:

```sql
CREATE USER 'watch'@'localhost' IDENTIFIED BY 'your-password';
GRANT SELECT ON `mydb`.`users` TO 'watch'@'localhost';
GRANT SELECT ON `mydb`.`settings` TO 'watch'@'localhost';
FLUSH PRIVILEGES;
```

Для PostgreSQL: `"driver": "postgres"` і рядок підключення на кшталт
`postgres://watch:password@127.0.0.1:5432/mydb?sslmode=disable`.

Імена таблиці та полів підставляються в запит як є (параметром їх передати
неможливо), тому вони перевіряються: лише літери, цифри та підкреслення.

### Журнал auditd

Розділ `audit`. Дає те, чого не видно ні обходом `/proc`, ні через inotify: ядро
повідомляє про кожен запуск програми з повним командним рядком і про кожне
відкриття файлу. Служба правил auditd не ставить - це робиться окремо (див.
`docs-auditd.md`):

```bash
auditctl -a always,exit -F arch=b64 -S execve -k sw_exec
auditctl -w /opt/myapp/.env.backup -p r -k sw_canary
```

Позначки правил задаються в `exec_keys` і `canary_keys`. Записи однієї події
ядро пише кількома рядками зі спільним номером, і служба збирає їх разом:
користувач і програма із SYSCALL, командний рядок із EXECVE, файл із PATH.

Події: `process_exec` (відомче), `process_exec_from_temp` (тривога),
`canary_file_read` (тривога, хтось прочитав файл-принаду).

### Дзеркало запитів

Розділ `mirror`. Веб-сервер пише до журналу лише рядок запиту, тому впровадження
в тілі POST і в заголовках у журналі не видно. nginx умієт надсилати копію
запиту до внутрішньої локації - служба її приймає, розбирає і відповідає відразу,
не затримуючи запит відвідувача.

```json
"mirror": {
  "enabled": true,
  "addr": "127.0.0.1:9777",
  "max_body_bytes": 65536,
  "privileged_fields": ["role_id", "is_admin", "balance", "status_id", "price"],
  "allow_paths": ["/admin/", "/api/admin/"]
}
```

Налаштування nginx:

```nginx
location / {
    mirror /_watch;
    mirror_request_body on;
    proxy_pass http://app_backend;
}

location = /_watch {
    internal;
    proxy_pass http://127.0.0.1:9777/mirror$request_uri;
    proxy_set_header X-Original-URI $request_uri;
    proxy_set_header X-Real-IP $remote_addr;
}
```

Що шукається в копії запиту:

- `mass_assignment_attempt` - у тілі запиту до шляху, якого немає в
  `allow_paths`, надійшло привілейоване поле. Імʼя поля шукається в тому
  вигляді, в якому надходить: `"role_id":` у JSON і `role_id=` у формі;
- ознаки впровадження в тілі та в заголовках;
- принади.

Подробиці налаштування й передавання відбитка TLS (JA3) - у
`docs-nginx-ja3.md`.

### Пастка

Розділ `trap`. Служба піднімає невеликий сервер і відповідає на адреси, на які
немає жодного посилання - ні в розмітці, ні в карті сайту, ні в `robots.txt`.
Потрапити на них випадково неможливо, тому саме звернення означає перебір.

```json
"trap": {
  "enabled": true,
  "addr": "127.0.0.1:9778",
  "paths": ["/.env.bak", "/admin-old", "/backup.sql"],
  "serve_bait": true,
  "bait_template": "APP_ENV=production\nDB_PASSWORD=%s\nAPI_KEY=%s\n"
}
```

Налаштування nginx:

```nginx
location ~ ^/(\.env\.bak|admin-old|backup\.sql)$ {
    proxy_pass http://127.0.0.1:9778;
    proxy_set_header X-Real-IP $remote_addr;
}
```

Подія `trap_hit` містить усе, що відвідувач надіслав сам: адресу, заголовки,
клієнта, перебрані шляхи. Коли ввімкнено `serve_bait`, йому віддається
правдоподібний файл налаштувань із підробленим ключем, власним для кожної
адреси. Ключ автоматично стає принадою: якщо ним потім спробують увійти, у подію
додається поле `bait_issued_to` - звʼязок між тим, хто копався, і тим, хто
намагається ввійти, доведений, а не припущений.

Без `serve_bait` пастка відповідає як звичайна відсутня адреса й нічим себе не
виказує. Накопичене за кожною адресою показує команда `-dossier`. Подробиці - у
`docs-trap.md`.

### Принади

Розділ `canary`. Принада - значення, якого в звичайному житті бути не може.
Підроблені облікові дані кладуть до підробленого файлу налаштувань на сервері:

```bash
cat > /opt/myapp/.env.backup <<'EOF'
DB_PASSWORD=CANARY_4F2A91C7E55B0D13
API_KEY=CANARY_4F2A91C7E55B0D13
EOF
```

```json
"canary": { "enabled": true, "tokens": ["CANARY_4F2A91C7E55B0D13"] }
```

Узяти таке значення більше ніде, тому його поява в запиті, у журналі застосунку
чи в копії запиту від дзеркала означає, що файли на сервері вже читали й
пробують знайдене. Подія `canary_used`, важливість найвища. Значення, коротше за
8 знаків, не враховується.

## Ознаки впровадження

Включаються `detect_injection` у розділах `access_log` та `app_log`, у дзеркалі
запитів працюють завжди. Перед порівнянням рядок розкодовується двічі (сканери
пишуть `%2527` замість `%27`), плюс замінюється пробілом, регістр зводиться до
нижнього.

| Вид | Важливість | Що шукає |
|---|---|---|
| `sqli_union` | alert | `union select`, `union all select` |
| `sqli_tautology` | alert | `' or 1=1`, `") and 1=1` |
| `sqli_comment` | warn | обрив запиту коментарем: `-- `, `#`, `/*!`, `; --` |
| `sqli_sleep` | alert | `sleep(`, `benchmark(`, `pg_sleep(`, `waitfor delay` |
| `sqli_schema` | alert | `information_schema`, `sysobjects`, `pg_catalog` |
| `sqli_file` | alert | `load_file`, `into outfile`, `into dumpfile`, `xp_cmdshell` |
| `sqli_stacked` | alert | `; drop`, `; insert`, `; update`, `; delete`, `; alter`, `; create` |
| `shell_injection` | alert | `;wget`, `curl` після розділювача, `; /bin/bash -c`, `$(...)`, зворотні лапки, `() { :; }` |
| `path_traversal` | alert | `../../`, `..\..\`, `/etc/passwd`, `/proc/self/environ` |
| `template_injection` | warn | `{{...}}`, `${jndi:` |

Набір розширюється й звужується налаштуваннями, без зміни коду:

```json
"access_log": {
  "extra_injection_patterns": [
    { "kind": "custom_backdoor", "pattern": "/cgi-bin/\\w+\\.cgi\\?cmd=", "severity": "alert" }
  ],
  "disabled_signatures": ["sqli_comment"]
}
```

Негодящий вираз із налаштувань пропускається: помилка друку не перешкоджає
запуску служби.

## Приймачі

Можна ввімкнути відразу кілька; відмова одного не перешкоджає решті.

```json
"sinks": {
  "file": "/var/log/security-watch/events.jsonl",
  "file_max_mb": 50,
  "file_keep": 7,
  "telegram": { "enabled": true, "token": "token", "chat_id": "chat id", "min_severity": "warn" },
  "email": {
    "enabled": true, "host": "smtp.example.com", "port": 587,
    "user": "watch@example.com", "pass": "password",
    "from": "watch@example.com", "to": ["admin@example.com"],
    "min_severity": "alert", "throttle": "15m"
  },
  "webhook": { "enabled": true, "url": "https://example.com/api/security-events", "headers": { "X-Token": "..." } },
  "outbox_max": 5000,
  "outbox_retry": "1m"
}
```

- **Файл** - одна подія в рядку у вигляді JSON. Працює без мережі. Служба ріже
  файл сама за `file_max_mb` і зберігає `file_keep` попередніх кусків, не
  покладаючись на зовнішній logrotate; доданий `logrotate.conf` потрібен лише
  там, де журнали ріжуть однаково.
- **Телеграм** - повідомлення через API бота, налаштованої пошти на сервері не
  потребує. Повідомлення, довші за 4096 знаків, обрізаються.
- **Пошта** - SMTP засобами стандартної бібліотеки, зі STARTTLS. Події
  накопичуються й виходять одним листом не частіше за `throttle`: під час навали
  це різниця між одним листом і сотнею.
- **HTTP-приймач** - POST із JSON і власними заголовками; зручно приймати події
  до власної панелі.

`min_severity` відсікає дрібниці: `alert` - лише тривоги, `warn` - тривоги й
попередження, порожньо - усе.

Усі мережеві приймачі (Телеграм, HTTP, пошта) обгорнуті чергою на диску: якщо
приймач недоступний, події лягають до `outbox.<приймач>.jsonl` і виходять за
першої можливості, не частіше за `outbox_retry`. Довжина черги обмежена
`outbox_max`, і в разі переповнення зберігаються найраніші події. Під час
зупинки служба надсилає те, що поштовий приймач тримав через термін затишшя, щоб
останню порцію не втратити при перезапуску.

Невдале надсилання враховується в `sink_errors` і показується командою
`-stats`.

Відмова приймача видна в журналі самої служби:

```
WARN sink did not accept the events sink=email events=1 error="535 5.7.8 Authentication Failed"
```

## Ланцюг подій

Кожна подія несе номер (`seq`), відбиток попередньої події (`prev_hash`) і свій
відбиток (`hash`), порахований за часом, джерелом, видом, адресою, предметом і
кількістю повторів. Вилучення або зміна запису рве ланцюг:

```bash
security-watch -verify /var/log/security-watch/events.jsonl
```

Команда або підтверджує цілість, або називає номер першого зіпсованого запису.
Файл налаштувань їй не потрібен, тому перевірку зручно запускати на власній
машині над надісланою копією журналу - тоді вона не залежить від сервера.

Номер і відбиток останньої події виходять назовні з ознакою життя. Номер може
лише зростати: номер, що зменшився, або відбиток, який не сходиться з надісланим
раніше, означають, що стан на сервері підмінили.

Події від спостерігачів проходять через чергу й обробляються по одній, тому
нумерація у файлі завжди відповідає порядку записів - включно з подією, що
народилася під час обробки іншої, як-от повідомлення про дійову особу. Черга
тримає 10000 подій; коли вона повна, спостерігачі чекають, бо вповільнити
читання журналів краще, ніж губити події.

## Дійові особи та рахунок

Розділ `actors`. Потік окремих подій не відповідає на питання "хто й що робить".
Служба зводить події за адресою: види та кількість подій, країна, власник
мережі, клієнти, відбиток TLS, перебрані шляхи, і рахує рахунок.

```json
"actors": {
  "enabled": true,
  "weights": { "honeypot_hit": 5, "trap_hit": 10, "sqli_union": 10, "ssh_login": 8 },
  "alert_score": 50,
  "digest_interval": "1h",
  "forget": "168h"
}
```

Вага виду події задається налаштуванням, те, чого немає в списку, важить 1. У
разі досягнення `alert_score` видається `actor_threshold` з усім, що відомо про
адресу. Раз на `digest_interval` виходить зведення. Адреса без нових подій
забувається через `forget`.

```bash
security-watch -config /etc/security-watch/config.json -actors
```

```
address              score  events last seen            what it did
203.0.113.77          1087     471 2026-11-01 09:53:57  honeypot_hit×68, request_flood×1, suspicious_path×402
```

## Навчання звичайної поведінки

Розділ `baseline`. Для частини того, що відбувається, немає готових ознак:
"адміністратор увійшов із країни, з якої ніколи не входив", "ключем API
скористався незнайомий клієнт". Служба задану кількість днів мовчки запамʼятовує
звичайні значення ознак, а потім повідомляє про значення, якого раніше не було.

```json
"baseline": {
  "enabled": true,
  "learn_days": 14,
  "features": ["country", "owner", "agent", "tls_fingerprint"],
  "kinds": ["ssh_login", "trap_hit", "mass_assignment_attempt", "canary_used"],
  "severity": "warn"
}
```

`features` беруться з подробиць події (`country`, `agent`, `ptr`, `owner`,
`tls_fingerprint`) і з самої події (`ip`, `subject`). `kinds` обмежує види
подій, за якими йде навчання. Поки навчання триває, служба під час запуску
повідомляє, скільки днів залишилося.

## Блокування

За замовчуванням служба не блокує нікого. Вона збирає пропозиції з доказами за
видами подій із `propose_on`:

```json
"blocking": {
  "enabled": true,
  "command": "ufw deny from %s",
  "unblock_command": "ufw delete deny from %s",
  "propose_on": ["trap_hit", "canary_used", "sqli_union", "path_traversal", "shell_injection", "mass_assignment_attempt"],
  "auto": { "enabled": false }
}
```

```bash
security-watch -config /etc/security-watch/config.json -candidates
security-watch -config /etc/security-watch/config.json -block 203.0.113.77
security-watch -config /etc/security-watch/config.json -unblock 203.0.113.77
```

`%s` у команді замінюється адресою; адресу перед підстановкою перевіряють як
IPv4 або IPv6. Команда може бути будь-якою: `ufw`, `nft`, виклик API Cloudflare
через `curl`.

**Самостійне блокування** включається окремо й з умовами:

```json
"auto": {
  "enabled": true,
  "min_hits": 3,
  "min_reasons": 2,
  "require_kinds": ["trap_hit", "canary_used"],
  "allowlist": ["203.0.113.5", "198.51.100.0/24"],
  "max_per_hour": 10,
  "dry_run": true
}
```

Умови потрібні, бо звернення до пастки не завжди означає напад: будь-хто може
розмістити в себе посилання на пастковий шлях, і браузер кожного, хто ту
сторінку відкриє, прийде з власної адреси. Один захід і один привід -
випадковість, кілька приводів і кілька заходів - перебір. `allowlist` розуміє
адреси й мережі, `max_per_hour` обмежує кількість блокувань за годину, а
`dry_run` друкує рішення (`auto_block_proposed`), нічого не виконуючи - так нові
умови обкатують без ризику.

## Дії у відповідь

Розділ `actions` - названі команди, які служба сама не викликає ніколи. Сенс у
тому, щоб відповідь на пригоду була однією командою:

```json
"actions": {
  "enabled": true,
  "commands": {
    "revoke-tokens": "mysql -u app -ppassword mydb -e \"DELETE FROM auth_access_tokens WHERE tokenable_id = %s\"",
    "ban-user": "mysql -u app -ppassword mydb -e \"UPDATE users SET is_banned = 1 WHERE id = %s\""
  }
}
```

```bash
security-watch -config /etc/security-watch/config.json -action revoke-tokens -arg 2648
```

Значення підставляється замість `%s` і перевіряється: дозволені літери, цифри,
точка, дефіс, підкреслення, двокрапка. Виконання дає подію `action_done`.

## Вивантаження журналу на інший сервер

Розділ `archive`. Раз на `interval` виконує вашу команду над файлом подій:

```json
"archive": {
  "enabled": true,
  "command": "rsync -az %s backup@another-server:/archive/security-watch/",
  "interval": "24h"
}
```

`%s` замінюється шляхом до файлу подій. Результат дає `archive_done` або
`archive_failed`.

## Захист самої служби

Розділ `self_guard`. Той, хто зламав сервер із правами root, найперше гасить
спостерігача або чистить його журнал. Проти цього працює пʼять речей:

1. **Події виходять назовні відразу** - те, що вийшло, вже не стерти.
2. **Ланцюг подій** - вилучений або підмінений запис видно під час перевірки.
3. **Служба стежить за власними файлами** - виконуваним файлом, налаштуваннями,
   unit systemd (`own_file_changed`, `own_file_missing`).
4. **Ознака життя** раз на `heartbeat_interval`. Її відсутність на приймальній
   стороні означає, що службу зупинили або сервер відрізали. Зупинка, якщо
   служба встигає, повідомляється подією `watch_stopped` найвищої важливості.
5. **Власні лічильники** у тій самій ознаці життя: скільки подій надійшло від
   спостерігачів, скільки приглушено правилами, склеєно, надіслано й скільки
   надсилань зірвалося. Без них "на сервері тихо" й "служба осліпла" виглядають
   однаково.

```bash
security-watch -config /etc/security-watch/config.json -stats
```

```
last change 2026-11-01 12:08:34
arrived 1140, delivered 715, suppressed 42, merged 396, failed deliveries 0
by severity:
  alert        135
  warn         577
by source:
  access       702
  auth         3
```

Чого це не дає: повної невразливості. Той, хто має root, може зупинити службу до
надсилання, підробити весь ланцюг або відрізати мережу. Сенс у тому, щоб тихе
прибирання слідів стало неможливим - будь-яка з цих дій сама стає помітною
подією.

Файли стану пишуться з правами 0600, файл налаштувань - 0640.

## Приглушення шуму

**Правила приглушення.** Подія, що збіглася з усіма заданими в правилі полями,
не видається взагалі; порожні поля не перевіряються.

```json
"ignore": [
  { "source": "process", "kind": "outbound_connection" },
  { "ip": "203.0.113.5" },
  { "source": "access", "kind": "path_scan", "ip": "198.51.100.10" },
  { "source": "files", "subject_contains": "/var/cache/" }
]
```

**Поправка важливості** за видом події - коли вид подій на цьому сервері
означає більше або менше за звичайне:

```json
"severity_overrides": { "sudo": "warn", "outbound_connection": "info", "ssh_login": "alert" }
```

**Склеювання повторів** працює завжди: та сама подія в межах `dedup_window`
надсилається один раз, а після закінчення вікна виходить одна подія з кількістю
накопичених повторів у полі `count`.

Для джерел, перелічених у `dedup_ignore_subject`, предмет події не входить до
ключа склеювання. Це важливо для перебору шляхів: шлях щоразу новий, тому з
предметом у ключі сканер, що обійшов 50 шляхів, давав близько сотні подій. За
замовчуванням (`access`, `trap`, `mirror`) той самий перебір дає три:
`honeypot_hit`, `suspicious_path` і `path_scan`, з кількістю повторів у `count`.
Для `files`, `db`, `ports` і `process` предмет залишається в ключі - два змінені
файли це дві різні події, а не повтор.

Отримана подія несе останній побачений предмет і кількість повторів; повний
перелік шляхів є в журналі веб-сервера, а для звернень до пастки - ще й у
досьє.

## Підбір порогів за власним трафіком

Пороги, узяті "із загальних міркувань", на одному сервері мовчать, на іншому
сиплють тривогами. Команда рахує їх за справжнім журналом:

```bash
security-watch -tune /var/log/nginx/access.log
```

Береться розподіл запитів за хвилинами й адресами, а поріг ставиться вище за
99,9-те значення, але нижче за рідкі викиди. Файл налаштувань не потрібен, тому
команду можна запускати й на власній машині над надісланою копією журналу.

## Файли та каталоги

| Шлях | Що |
|---|---|
| `/opt/security-watch/security-watch` | виконуваний файл |
| `/etc/security-watch/config.json` | налаштування, права 0640 |
| `/var/lib/security-watch/` | позначки прочитаного, зліпки файлів і полів, ланцюг, досьє, пропозиції щодо блокування, черги ненадісланого, лічильники; права 0600 |
| `/var/log/security-watch/events.jsonl` | журнал подій |
| `/etc/systemd/system/security-watch.service` | служба |
| `/etc/logrotate.d/security-watch` | нарізка журналу подій зовнішнім logrotate |

Стан можна вилучити цілком: служба заново візьме зліпки й продовжить роботу.
Перший прохід після цього подій не дає.

## Витрата ресурсів

Заміри на сервері з nginx, застосунком на Node.js, MariaDB і десятком служб, за
2170 рядків у журналі веб-сервера на добу:

| Що | Скільки |
|---|---|
| Памʼять | 14,3-14,6 МБ |
| Процесорний час | 3 с на розбір накопиченого журналу під час запуску, далі простій |
| Один прохід `-once` файлами, портами, процесами та базою | 2,4 с |
| Стеження в реальному часі | 469 каталогів під inotify |
| Розмір однієї події в журналі | близько 470 байтів |
| Виконуваний файл | 7,8 МБ із `-ldflags='-s -w'`, 11,1 МБ без них |

## Сумісність

- **ОС**: Linux - Ubuntu, Debian, RHEL і похідні. Збірка під інші системи
  можлива, стеження в реальному часі й читання `/proc` при цьому вимикаються.
- **Веб-сервери**: nginx, apache та будь-які інші. Формат combined розуміється з
  коробки, решта - через `regexp`. Дзеркало тіла запиту потребує nginx із
  директивою `mirror`.
- **Застосунки**: служба не знає нічого про фреймворк. Для журналу застосунку
  потрібен лише шлях до файлу; підстановка привілейованих полів ловиться за
  іменами полів, які задаєте ви, тому працює однаково з Laravel, AdonisJS,
  Django та Rails.
- **СУБД**: MySQL, MariaDB, PostgreSQL.
- **Доставка**: Телеграм, SMTP, власний HTTP-приймач, файл.

## Збірка та перевірки

```bash
go build -o security-watch ./cmd/security-watch   # збірка
go build -ldflags="-X main.version=1.0.0" -o security-watch ./cmd/security-watch   # збірка з версією
go test ./...                                     # перевірки
go test -race ./...                               # перевірки з пошуком гонок
go test -cover ./internal/watch                   # покриття
go vet ./...                                      # вбудований аналізатор
staticcheck ./...                                 # зовнішній аналізатор
gosec ./...                                       # розбір на небезпечні прийоми
```

Будова: `cmd/security-watch` розбирає командний рядок, `internal/watch` робить
усю роботу. Залежності: драйвери `go-sql-driver/mysql` і `lib/pq`, решта -
стандартна бібліотека.

## Відомі обмеження

Перелічено те, що перевірено. Шість дефектів, знайдених на робочому сервері,
виправлено й покрито перевірками; нижче - чесний залишок.

1. **Склеєна подія несе лише останній предмет.** Для джерел із
   `dedup_ignore_subject` подія містить останній побачений шлях і кількість
   повторів; повний перелік шляхів доводиться шукати в журналі веб-сервера або в
   досьє для звернень до пастки.
2. **Повна черга вповільнює спостерігачів.** Черга подій тримає 10000 записів.
   Якщо приймачі не встигають (наприклад, повільний сервер SMTP), читання
   журналів чекає. Це свідомий вибір: краще загальмувати, ніж губити події.
   Перевірено: прохід по 12000 змінених файлів дає 12000 подій із цілим
   ланцюгом і займає 11 секунд замість 1.
3. **`internal/watch` - один пакет приблизно на 6600 рядків.** Внутрішні
   залежності не розділені на окремі пакети.
4. **Покриття 76,7%** для рушія та 28,8% для обгортки командного рядка.
5. **Служба має близько доби справжньої роботи** на одному сервері. Пороги
   отримані зі справжнього журналу, але підтвердити їх може лише робота.
6. **Доставку пошти підтверджують перевірки, а не лист.** Поштовий приймач
   покритий перевірками з підміненим надсиланням; живі спроби зриваються на боці
   поштового провайдера (`535 Authentication Failed`), що лежить поза службою.
   Такі події чекають у `outbox.email.jsonl` і повторюються не частіше за термін
   затишшя, тому хибний пароль відкладає повтор на цей термін.
7. **Читання справжньої адреси клієнта потребує зміни в nginx.**
   `real_ip_field` працює лише після того, як адресу додано до `log_format`; без
   цього служба бачить адреси проксі.
